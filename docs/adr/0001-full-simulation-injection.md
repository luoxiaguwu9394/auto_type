# 采用全仿真键盘注入，而不是粘贴或控件设值

`auto_type` 存在的唯一前提，就是目标输入区可能不收粘贴。有些网页输入框禁掉了 paste 事件，有些应用压根不接受直接设值。所以语料的每个字符都作为独立按键事件送进系统输入队列，一次一个——不用剪贴板，也不直接给控件设值。代价是慢（5 万字按 55ms/字约 45 分钟），换来的是任何接受真实键盘的目标都能用，包括禁用粘贴的表单、游戏和远程桌面。

## Status

accepted

## 已知的例外

路线图里的"超长语料走剪贴板加速"是本决策唯一预留的出口：它**不**改变默认路径，只在先探测到目标确实接受粘贴时才启用，且必须由使用者显式选择。除此之外不要往这条路退。

## Considered Options

- **剪贴板粘贴（Ctrl+V）**：快两个数量级，但被禁粘贴的目标直接失效，而且看不到打字过程，失去了这个工具的意义。
- **`WM_SETTEXT` / UI Automation `SetValue`**：瞬间完成，但绕过真实输入队列，游戏、远程桌面、多数现代应用不认，也不触发 JS 的 keydown/input 事件和字数统计。
- **走输入法逐字敲**：最像真人，但依赖输入法当前状态，极慢且不可靠，中文场景下没有收益。
- **UI Automation 定位控件后再注入**：连"定位"这一步都不可靠——大量中文软件是自绘 UI，没有标准控件树。这也是本工具让使用者手动放光标的原因。

## Consequences

- 语料必须逐字符遍历，性能上限由节奏决定，不存在"一次性写入"的优化空间。
- 中文走 Unicode 按键事件直接发，不经输入法；emoji 与部分生僻字需要拆成 UTF-16 代理对发送。
- 敲字期间目标窗口必须在前台，否则字会打进错误的窗口——因此必须有焦点监护（见 `GLOSSARY.md`）。
- 拟人（抖动、回退、行间停顿）只能在"逐字符"这个前提下实现，反过来强化了本决策。
